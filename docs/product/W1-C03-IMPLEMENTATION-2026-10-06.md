The foundation records a request before an effect. The resource change, required material event and accepted completion then use one dedicated database transaction. Replay reads that completion under the same current lock; reconciliation invokes no business mutator. A lost acknowledgement remains uncertain until a replacement session reads the original durable facts. Publication is separate, profile-defined and idempotent.

Development identity is `1.0.0-dev.wave1-operation-storage.1`. No generic retrofit of scoped save/reset, existing audit-token completion, checkout, Woo order writes, rule publication, email/payment/carrier effects or external exactly-once promise is made. Existing COR-005/COR-007 behavior stays separate.

Completion and event formats are independently versioned and bounded to 16,384 encoded bytes, depth eight and 256 value nodes. Unknown keys/types/versions, duplicate JSON keys, renamed/nested private facts and inconsistent state/event links refuse without rewriting the stored original. Stored errors contain only safe C01 vocabulary/parameters/violations; replay reconstructs current attempt IDs. The immutable event retains the first accepted effect's request/correlation IDs.

The native session currently verifies ownership using `@@in_transaction`. An unsupported server introspection capability refuses **this new feature**; it does not change legacy database availability or establish broad native MySQL compatibility. Custom routing/replica drop-ins likewise require an explicit equivalent authoritative factory. Local MariaDB evidence cannot substitute for the final CI runtime.

## Preservation and scope

Both new operation stores preserve pending, accepted, rejected and no-change records and referenced material events. There is no TTL, age takeover, purge worker or destructive rollback. They stay outside `ConfigurationTables::all_suffixes()` and both existing delete allowlists, including explicit-delete uninstall. Default deactivate/uninstall and writer-disable rollback preserve them.

This new-store policy does **not** rewrite the historical explicit-delete policy for legacy configuration/audit tables. Existing scoped completions are unchanged by this implementation; the old explicit-delete allowlist remains distinct from ordinary retention. C06 still owns the complete inventory and any later governed retention/deletion decision. No claim that C03 completes the whole data-lifecycle requirement family is made.

## Findings closed during implementation

- A pending record with an orphan material event could evade an audit-ID-only lookup. Current-lock hydration now also reads the event by same-site operation identity and refuses that inconsistent pair without rewriting it.
- A corrupt immutable target digest was incorrectly combined with genuine changed intent. Immutable identity mismatch now reports uncertainty; only the separately compared intent fingerprint produces `intent_conflict`.
- Revocation after acknowledged effect/marker COMMIT, or during a failed publisher, must hide private receipt facts without claiming the committed mutation was rejected. The coordinator retains durable accepted truth and returns an uncertain response with no private completion. The corresponding coordinator methods and SQL post-commit revocation case above preserve this distinction.
- Session transaction introspection is checked rather than inferred. Unsupported introspection, session changes, ambient ownership, deadlock-ended units and retirement failures cannot be silently treated as an owned transactional success.
